# MITRE and the ATT&CK Framework

MITRE is a **not-for-profit organization** that performs research in areas such as cybersecurity, artificial intelligence, healthcare, and space systems.

In cybersecurity, MITRE provides frameworks and knowledge bases that help security professionals **understand attacker behavior and improve defenses**.

This room mainly covers:

* MITRE ATT&CK
* CAR Knowledge Base
* D3FEND
* MITRE Engage

The main focus is the **MITRE ATT&CK Framework**.


# What is MITRE ATT&CK?

MITRE ATT&CK is a globally accessible knowledge base of **real-world attacker tactics and techniques**.

ATT&CK stands for:

**Adversarial Tactics, Techniques, and Common Knowledge**

MITRE studies real cyberattacks and documents **how attackers actually behave**.

So, think of MITRE ATT&CK as an **organized encyclopedia of attacker behavior**.

For example, attackers may:

* Scan a target.
* Send phishing emails.
* Execute PowerShell.
* Steal credentials.
* Escalate privileges.
* Maintain persistence.
* Exfiltrate data.

MITRE organizes these attacker behaviors into a structured framework.

Both **Red Teams and Blue Teams** use ATT&CK.

**Red Teams** use it to plan realistic attack simulations.

**Blue Teams** use it to understand attacker behavior and create better detections and defenses.

# Understanding TTPs

One of the most important concepts in MITRE ATT&CK is **TTP**.

**TTP = Tactics, Techniques, and Procedures**

| Term          | Simple Meaning                        | Question     |
| ------------- | ------------------------------------- | ------------ |
| **Tactic**    | Attacker's goal                       | Why?         |
| **Technique** | Method used to achieve the goal       | How?         |
| **Procedure** | Exact implementation of the technique | How exactly? |

### Tactic

A **Tactic** represents the attacker's goal or objective.

It answers:

> **Why is the attacker doing this?**

Examples include reconnaissance, credential access, persistence, and privilege escalation.

Suppose the attacker wants to collect information about a company.

The goal is **Reconnaissance**.

Therefore:

**Tactic = Reconnaissance**

### Technique

A **Technique** describes how the attacker achieves the tactic.

It answers:

> **How will the attacker achieve the goal?**

For example, the attacker wants to perform reconnaissance.

They may perform **Active Scanning**.

Therefore:

**Tactic = Reconnaissance**

**Technique = Active Scanning**

### Procedure

A **Procedure** explains how a real attacker or threat group actually implemented a technique.

For example, a threat actor may use a specific tool or command to scan the target's network.

Therefore:

**Tactic = Why**

**Technique = How**

**Procedure = How exactly it was performed**

The easiest way to remember TTP is:

> **Goal → Method → Actual Implementation**

# Evolution of MITRE ATT&CK

MITRE ATT&CK was introduced in **2013** to document the common Tactics, Techniques, and Procedures used by advanced attackers, including **Advanced Persistent Threat (APT) groups**.

Initially, ATT&CK mainly focused on **Windows systems**.

Later, it expanded to cover many environments.

The **Enterprise ATT&CK Matrix** now includes environments such as:

* Windows
* Linux
* macOS
* Cloud platforms

MITRE also provides specialized ATT&CK knowledge bases for:

* Mobile systems
* Industrial Control Systems (ICS)

The framework continues to grow using real-world observations and contributions from the cybersecurity community.

# What is the ATT&CK Matrix?

The **ATT&CK Matrix** is a visual representation of attacker tactics and techniques.

The matrix organizes attacker behavior in a structured format.

At the top of the matrix, you see **Tactics**.

Under each tactic, you see related **Techniques**.

Some techniques can be expanded into more specific **Sub-techniques**.

The structure is:

**Tactic → Technique → Sub-technique**

# Example: Reconnaissance

Suppose an attacker wants to gather information about a target.

The attacker's goal is:

**Tactic: Reconnaissance**

The attacker decides to actively scan the target.

The method is:

**Technique: Active Scanning**

Active Scanning can be performed in several specific ways.

These are **Sub-techniques**:

* Scanning IP Blocks
* Vulnerability Scanning
* Wordlist Scanning

So the structure is:

**Reconnaissance → Active Scanning → Vulnerability Scanning**

Here:

**Reconnaissance** is the goal.

**Active Scanning** is the method.

**Vulnerability Scanning** is a more specific version of that method.

# Technique IDs

Each MITRE ATT&CK technique has a unique **Technique ID**.

For example, **Active Scanning** has its own ATT&CK ID.

You will often see MITRE technique IDs when reading:

* Threat intelligence reports.
* Malware analysis reports.
* SOC alerts.
* SIEM detections.
* Incident response reports.

The ID helps security professionals refer to the **same attacker technique using a standard name**.

# What Information Does ATT&CK Provide?

When you open a technique page in the [MITRE ATT&CK website](https://attack.mitre.org/?utm_source=chatgpt.com), you can find information such as:

* Technique description.
* Technique ID.
* Sub-techniques.
* Procedure examples.
* Threat groups that used the technique.
* Software or malware associated with the technique.
* Campaigns.
* Mitigations.
* Detection methods.
* References.

For example, a defender can study a technique and ask:

> How do attackers perform this technique?

Then:

> How can we detect this behavior?

And finally:

> How can we reduce or mitigate the attack?

This is why ATT&CK is extremely useful for **SOC Analysts, Threat Hunters, Threat Intelligence Analysts, Incident Responders, and Red Teams**.

# ATT&CK Navigator

The **ATT&CK Navigator** is a tool used to explore and annotate the ATT&CK Matrix.

Security professionals can use it to:

* Highlight techniques.
* Map attacker behavior.
* Map threat groups.-
* Compare security coverage.
* Identify detection gaps.

For example, if a threat group uses 15 ATT&CK techniques, a security team can highlight those techniques and check:

> **Can our organization detect all 15 techniques?**

If the organization cannot detect five of them, those five techniques represent possible **detection gaps**

# Why MITRE ATT&CK Matters

Now we know that MITRE ATT&CK contains information about attacker **Tactics, Techniques, and Procedures (TTPs)**.

The next question is:

**Why do cybersecurity teams actually use ATT&CK?**

The main reason is that ATT&CK provides a **common and standard language for describing attacker behavior**.

In cybersecurity, the same attacker action may be called by different names by different security companies or researchers. This can create confusion.

ATT&CK solves this by giving attacker techniques:

* A standard name.
* A clear description.
* A unique technique ID.

Because everyone uses the same terminology, security teams can easily compare threat reports, incidents, and detection information.

For example, instead of different security teams using different names for the same behavior, they can simply refer to the same **ATT&CK technique and technique ID**.

# Threat Intelligence and Defense

ATT&CK also connects **Cyber Threat Intelligence (CTI)** with real defensive security operations.

A threat intelligence report may explain:

**"The attacker used PowerShell to execute malicious commands."**

This information is useful, but a defender still needs to understand:

**How can we detect this behavior in our organization?**

Security teams can map the attacker behavior to a MITRE ATT&CK technique.

The process is:

**Threat Report → Identify Attacker Behavior → Map to ATT&CK TTP → Create Detection**

Once the behavior is mapped, defenders can create:

* SIEM detection rules.
* EDR detection rules.
* Detection queries.
* Investigation playbooks.
* Incident response procedures.

So ATT&CK helps convert **threat intelligence into practical defensive actions**.

# Who Uses MITRE ATT&CK?

Different cybersecurity teams use ATT&CK for different purposes.

| Team                   | Main Goal                   | How They Use ATT&CK                                     |
| ---------------------- | --------------------------- | ------------------------------------------------------- |
| **CTI Team**           | Understand threat actors    | Map attacker behavior to ATT&CK TTPs                    |
| **SOC Analyst**        | Investigate security alerts | Connect suspicious activity to tactics and techniques   |
| **Detection Engineer** | Build security detections   | Map SIEM and EDR rules to ATT&CK techniques             |
| **Incident Responder** | Investigate cyber incidents | Map the attack timeline to ATT&CK                       |
| **Red Team**           | Simulate attackers          | Create attacks based on real ATT&CK techniques          |
| **Purple Team**        | Improve defenses            | Test whether security controls detect ATT&CK techniques |

### Cyber Threat Intelligence Teams

CTI teams collect and analyze information about attackers and threat groups.

They study:

* Tools used by attackers.
* Malware.
* Attack methods.
* Targeted organizations.
* Tactics and techniques.

They then map this behavior to ATT&CK TTPs.

This creates a **threat actor profile** that other security teams can understand and use.

### SOC Analysts

SOC analysts investigate security alerts.

They map suspicious activity to ATT&CK tactics and techniques to better understand **what the attacker may be trying to achieve**.

For example, an alert related to credential dumping may indicate that the attacker is attempting **Credential Access**.

ATT&CK provides extra context to the alert.

### Detection Engineers

Detection engineers create security detection rules.

They work with tools such as:

* SIEM.
* EDR.
* IDS.

They map detection rules to ATT&CK techniques.

For example:

**Detection Rule → Detect PowerShell Behavior → Map to ATT&CK Technique**

This helps the organization identify which attacker techniques it can detect and where detection gaps exist.

### Incident Responders

Incident responders investigate cyberattacks.

They map the attack timeline to ATT&CK tactics and techniques.

For example:

**Phishing → Execution → Persistence → Credential Access → Exfiltration**

Mapping the incident to ATT&CK helps the team clearly visualize **how the attack progressed**.

### Red and Purple Teams

Red Teams simulate real attackers.

They use ATT&CK to create realistic attack plans based on known attacker behavior.

Purple Teams combine offensive and defensive knowledge.

They use ATT&CK to test questions such as:

**Can our security tools detect this technique?**

If not, the Blue Team improves its detection.

# Mapping an Attack to ATT&CK

Suppose an organization suffers a cyberattack.

After the incident, the security team investigates how the attack happened.

Instead of writing an unstructured description, they map each attacker action to ATT&CK.

For example:

**Phishing → Scheduled Task → File Obfuscation → Tool Transfer**

Each attacker behavior is mapped to a specific ATT&CK technique.

This helps the organization:

* Understand the complete attack.
* Identify the attacker's preferred techniques.
* Find detection gaps.
* Improve security controls.
* Prepare for future attacks.

# Mustang Panda Example

Mustang Panda is a threat group identified in MITRE ATT&CK as **G0129**.

Based on observed attacks, researchers have mapped its behavior to several ATT&CK techniques.

The example in the room shows that Mustang Panda has used behaviors such as:

**Initial Access:** Phishing.

The group uses phishing techniques to gain initial access to a target.

**Persistence:** Scheduled Tasks.

Scheduled tasks can be used to repeatedly execute malicious code and maintain access.

**Defense Evasion:** Obfuscated Files.

Malicious files or information may be hidden or modified to make detection more difficult.

**Command and Control:** Ingress Tool Transfer.

Tools or files can be transferred into the compromised environment to support later attacker activities.

These observed behaviors are mapped to ATT&CK techniques.

Security teams can then use the [ATT&CK Navigator](https://mitre-attack.github.io/attack-navigator/?utm_source=chatgpt.com) to visually explore and analyze the mapped techniques.

# Cyber Analytics Repository (CAR)

The **Cyber Analytics Repository (CAR)** is a collection of **ready-made detection analytics** created by MITRE.

The simplest way to remember CAR is:

> **ATT&CK tells us what attackers do. CAR helps defenders detect that behavior.**

For example, MITRE ATT&CK may tell us:

**Attackers use Scheduled Tasks for persistence.**

As a defender, we ask:

**What activity should I search for in my logs to detect this?**

CAR gives us a **detection idea and example search logic**.

The basic flow is:

**ATT&CK Technique → CAR Analytic → Detection Logic → SIEM Detection**

## What is a CAR Analytic?

A **CAR Analytic** describes how to detect a particular attacker behavior.

It can explain:

* What suspicious behavior to look for.
* Why the behavior may be malicious.
* Which ATT&CK tactic and technique are related.
* What detection logic to use.
* Example searches for security tools.

So, a CAR analytic is basically a **detection guide for defenders**.

# Example: CAR-2020-09-001

The room examines:

**CAR-2020-09-001: Scheduled Task - File Access**

`CAR-2020-09-001` is the **unique ID of the detection analytic**.

The analytic focuses on detecting suspicious activity related to **Windows Scheduled Tasks**.

Attackers may use Scheduled Tasks to automatically execute malicious commands or programs.

This behavior can be related to the ATT&CK tactics:

* **Execution**
* **Persistence**
* **Privilege Escalation**

The related technique is:

**Scheduled Task/Job**

The main detection idea is to watch for suspicious file activity in Windows Scheduled Task locations.

Windows stores Scheduled Task files in locations such as:

**C:\Windows\System32\Tasks**

and

**C:\Windows\Tasks**

If an unusual process creates or accesses files in these folders, the activity may require investigation.

# Implementations

The **Implementations** section explains how an analyst can turn the detection idea into a practical detection.

For this CAR analytic, examples include:

* Pseudocode
* Splunk query
* LogPoint search

Not every CAR analytic provides the same implementations.

Some may support Splunk, while others may contain EQL or different detection formats.

The main idea is:

> **The detection behavior stays the same, but the query syntax changes depending on the security tool.**

## What is Pseudocode?

**Pseudocode** is a human-readable way of explaining program or detection logic.

It is mainly used to help people understand **what the detection is trying to do**.

For this CAR analytic, the pseudocode is basically saying:

1. Search for file creation events.
2. Find files created inside Windows Scheduled Task folders.
3. Check which process created the file.
4. Ignore expected normal system activity.
5. Show suspicious results.

So the detection logic is:

**Search File Creation → Check Task Folder → Filter Normal Activity → Show Suspicious Activity**

Pseudocode is usually **not executed directly**.

It explains the logic in a simple way.

## Splunk Query

[Splunk](https://www.splunk.com/?utm_source=chatgpt.com) is commonly used to search and analyze security logs.

CAR may provide a Splunk query that analysts can use or modify for their environment.

For this example, the Splunk search looks for file creation activity inside the Windows Scheduled Task directories.

It also filters expected activity from a normal Windows process such as `svchost.exe`.

In simple words, the Splunk query asks:

> **Show me unusual processes creating Scheduled Task files.**

If suspicious activity is found, a SOC analyst can investigate it.

## LogPoint Search

[Logpoint](https://www.logpoint.com/?utm_source=chatgpt.com) is another SIEM and security analytics platform.

CAR may also provide a LogPoint search for the same attacker behavior.

So:

**Same attacker behavior → Same detection idea → Different SIEM query syntax**

For example:

**CAR Detection Logic → Splunk Query**

or

**CAR Detection Logic → LogPoint Search**

## What are Unit Tests?

Some CAR analytics include **Unit Tests**.

A Unit Test is used to check whether the analytic works correctly.

For example:

1. Generate known Scheduled Task activity.
2. Run the detection.
3. Check whether the detection identifies the activity.

If the detection finds the test activity, it is working as expected.

So remember:

**Unit Test = Validate whether the detection works**

# MITRE D3FEND

With MITRE ATT&CK, we learn **how attackers attack**.

With MITRE D3FEND, we learn **how defenders can defend against attacker behavior**.

The easiest way to remember is:

> **ATT&CK = Attacker's side**

> **D3FEND = Defender's side**

For example, ATT&CK may tell you:

**An attacker steals user credentials.**

Now the defender asks:

**What defensive techniques can reduce the damage from stolen credentials?**

D3FEND helps answer this question.


# What is D3FEND?

**D3FEND** stands for:

**Detection, Denial, and Disruption Framework Empowering Network Defense**

It is a defensive cybersecurity framework created by MITRE.

D3FEND contains structured information about **defensive techniques**.

It explains:

* What the defensive technique is.
* How the defense works.
* What security artifacts it affects.
* What should be considered when implementing it.
* How the defense relates to ATT&CK techniques.

D3FEND also provides a **common language for defenders**.

Just like ATT&CK gives standard names and IDs to attacker techniques, D3FEND gives standard names and IDs to defensive techniques.

# D3FEND Matrix

D3FEND has its own [D3FEND Matrix](https://d3fend.mitre.org/?utm_source=chatgpt.com).

The matrix contains **seven defensive tactics**:

| Tactic      | Simple Meaning                               |
| ----------- | -------------------------------------------- |
| **Model**   | Understand and represent the system.         |
| **Harden**  | Make the system more secure.                 |
| **Detect**  | Identify suspicious or malicious activity.   |
| **Isolate** | Separate a threat or compromised system.     |
| **Deceive** | Mislead or confuse attackers.                |
| **Evict**   | Remove attackers from the environment.       |
| **Restore** | Return systems to a normal and secure state. |

These tactics describe the **defender's goals**.

## Model

**Model** means understanding your systems and environment.

For example:

* Identify devices.
* Understand network connections.
* Understand normal system behavior.
* Identify important digital assets.

Before protecting something, the security team must understand **what exists in the environment**.

## Harden

**Harden** means making systems more difficult to attack.

Examples include:

* Strong passwords.
* Secure configurations.
* Disabling unnecessary services.
* Applying security controls.

The goal is to **reduce attack opportunities**.

## Detect

**Detect** means identifying suspicious or malicious activity.

Examples include:

* Monitoring logs.
* Detecting unusual processes.
* Detecting suspicious network traffic.
* Detecting malicious files.

The goal is to **discover attacker activity**.

## Isolate

**Isolate** means separating a compromised system or threat from the rest of the environment.

For example, if a computer is infected with malware, the security team may disconnect it from the network.

This helps prevent the attack from spreading.

## Deceive

**Deceive** means misleading the attacker.

For example, defenders may create fake systems, fake credentials, or fake information.

If attackers interact with these fake resources, defenders can detect their activity.

## Evict

**Evict** means removing the attacker from the environment.

Examples include:

* Terminating malicious processes.
* Removing malware.
* Deleting attacker accounts.
* Revoking compromised credentials.

The goal is to **remove attacker access**.

## Restore

**Restore** means returning systems to a secure and normal working state.

Examples include:

* Restoring data from backups.
* Rebuilding compromised machines.
* Recovering damaged systems.
* Returning business operations to normal.

# Example: Credential Rotation

The TryHackMe section gives the example:

**Credential Rotation – D3-CRO**

`D3-CRO` is the D3FEND technique ID.

**Credential Rotation** means regularly changing passwords or other authentication credentials.

Suppose an attacker steals a user's password.

The attacker may try to use that password again later.

If the organization changes the password, the stolen credential may no longer work.

For example:

**Attacker steals password → Password is rotated → Old password becomes invalid → Attacker cannot reuse it**

This helps reduce the risk of **credential reuse by attackers**.

# How Credential Rotation Works

Imagine a user's password is:

**Sai@123**

An attacker steals this password.

The attacker now has valid credentials.

Later, the organization rotates the user's password.

The new password becomes different.

Now:

**Old stolen password = Invalid**

**New password = Valid**

If the attacker tries the stolen password again, authentication should fail.

This is the basic idea behind **Credential Rotation**.

# Digital Artifact Relationships

D3FEND also explains relationships with **Digital Artifacts**.

A digital artifact is a digital object or piece of data involved in a system.

Examples include:

* Credentials.
* Files.
* Processes.
* Network traffic.
* User accounts.
* Configuration data.

For Credential Rotation, the important digital artifact is the **credential**.

The defensive technique changes or replaces the credential so an old credential cannot continue to be reused.

This relationship helps defenders understand:

> **What part of the system does this defensive technique protect or modify?**

# ATT&CK and D3FEND Together

The most important idea is that ATT&CK and D3FEND show **two sides of cybersecurity**.

| MITRE ATT&CK         | MITRE D3FEND              |
| -------------------- | ------------------------- |
| Attacker behavior    | Defender behavior         |
| How attackers attack | How defenders protect     |
| Offensive techniques | Defensive techniques      |
| Attacker TTPs        | Defensive countermeasures |
| Attacker's move      | Defender's response       |

# Other MITRE Cybersecurity Projects

Beyond **ATT&CK, CAR, and D3FEND**, MITRE provides other projects that help security professionals:

* Simulate real attackers.
* Test security defenses.
* Practice incident response.
* Understand threats to newer technologies.

The main projects in this section are **Adversary Emulation Plans, Caldera, AADAPT, and ATLAS**.

## Adversary Emulation Plans

An **Adversary Emulation Plan** is a step-by-step plan for **simulating the behavior of a real threat group**.

The [Adversary Emulation Library](https://ctid.mitre.org/resources/adversary-emulation-library/?utm_source=chatgpt.com) contains emulation plans based on known attacker groups and is primarily maintained and contributed to by Center for Threat-Informed Defense.

Suppose a known APT group normally performs:

**Phishing → PowerShell Execution → Credential Theft → Persistence**

The emulation plan explains how a security team can **mimic that group's known behavior in a controlled and authorized environment**.

The main purpose is to test:

**Can our organization detect this attacker's behavior?**

Red Teams can follow the plan to simulate the threat group.

Blue Teams can monitor the activity and check whether their security tools detect it.

So remember:

> **Emulation Plan = Step-by-step guide to mimic a known threat group's behavior**

## Caldera

[MITRE Caldera](https://caldera.mitre.org/?utm_source=chatgpt.com) is an **automated adversary emulation platform**.

Instead of manually performing every attack simulation step, Caldera can automate adversary behavior based on ATT&CK techniques.

For example, a security team may want to test:

**Can our EDR detect a specific attacker technique?**

Caldera can simulate ATT&CK-aligned behavior in a controlled test environment.

The security team then checks whether:

* EDR generates an alert.
* SIEM receives relevant logs.
* SOC analysts identify the activity.
* Incident responders react correctly.

The simple flow is:

**Choose Attacker Behavior → Caldera Simulates Activity → Security Tools Monitor → Team Checks Detection**

Caldera is useful for both offensive and defensive security exercises.

**Red Team:** Simulate attacker behavior.

**Blue Team:** Detect and investigate the simulated activity.

**Purple Team:** Run the simulation and improve detection together.

The easiest way to remember is:

> **Caldera = Automated attacker simulation using ATT&CK**

## Emulation Plan vs Caldera

| Emulation Plan                       | Caldera                                |
| ------------------------------------ | -------------------------------------- |
| Step-by-step attack simulation guide | Automated adversary emulation platform |
| Explains how to mimic a threat group | Executes ATT&CK-aligned simulations    |
| More like an attack plan             | More like an automation tool           |
| Used to design realistic exercises   | Used to run and test exercises         |

In simple words:

**Emulation Plan = Instructions**

**Caldera = Automation Tool**

## AADAPT

MITRE AADAPT stands for:

**Adversarial Actions in Digital Asset Payment Technologies**

AADAPT is a knowledge base focused on attacks against **digital asset technologies**.

It covers threats related to:

* Blockchain networks.
* Smart contracts.
* Digital wallets.
* Digital asset management systems.

AADAPT has its own matrix and follows a structure similar to ATT&CK.

For example:

**ATT&CK → General attacker behavior**

**AADAPT → Attacker behavior targeting digital asset technologies**

The main goal is to help defenders understand and reduce threats targeting blockchain and digital asset environments.

> **AADAPT = ATT&CK-style knowledge base for digital asset and blockchain threats**

## ATLAS

MITRE ATLAS stands for:

**Adversarial Threat Landscape for Artificial-Intelligence Systems**

ATLAS focuses on threats against **Artificial Intelligence and Machine Learning systems**.

It documents:

* Real-world AI attack techniques.
* AI and ML vulnerabilities.
* Adversary behavior.
* Defensive mitigations.

For example, attackers may attempt to manipulate or abuse AI systems.

ATLAS helps security professionals understand:

**How was the AI system attacked?**

**What technique did the attacker use?**

**How can the risk be reduced?**

ATLAS also provides its own matrix, similar to the ATT&CK Matrix.

> **ATLAS = ATT&CK-style framework for AI and Machine Learning security threats**
