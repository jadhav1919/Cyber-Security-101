# Introduction to SIEM

Organizations have many devices connected to their network, such as:

* Computers
* Servers
* Firewalls
* Routers
* Switches
* Web servers
* Applications

Each of these devices generates **logs**.

If security analysts had to check each device separately, detecting attacks would be slow and difficult.

To solve this problem, organizations use a **SIEM (Security Information and Event Management)** system.

 

# What is SIEM?

**SIEM (Security Information and Event Management)** is a centralized security solution that collects, stores, analyzes, and correlates logs from multiple devices to detect security incidents.

It is one of the most important tools used by **SOC (Security Operations Center)** analysts.

 
# Why Do We Need SIEM?

Without SIEM:

* Logs are stored on different devices.
* Analysts must investigate each device individually.
* Detecting attacks becomes slow.
* Important events may be missed.

With SIEM:

* Logs are collected in one place.
* Events are correlated automatically.
* Suspicious activities are detected quickly.
* Alerts are generated automatically.

# Logs Everywhere

Every device in a network continuously performs activities such as:

* User logins
* File access
* Process execution
* Website visits
* Network communication

Each activity generates a **log**.

These devices that generate logs are called **Log Sources**.

# What is a Log Source?

A **Log Source** is any device, application, or network component that generates logs.

Examples include:

* Windows computers
* Linux servers
* Firewalls
* Routers
* IDS/IPS
* Web servers
* Databases

# Types of Log Sources

There are **two main categories** of log sources:

1. Host-Centric Log Sources
2. Network-Centric Log Sources


# 1. Host-Centric Log Sources

These logs record activities that happen **inside a device (host)**.

### Devices

* Windows systems
* Linux systems
* Servers
* Workstations

### Common Events

* User login/logout
* File access
* Process execution
* Registry modifications (Windows)
* PowerShell execution
* Software installation

### Example

A user logs into a Windows computer and opens a confidential document.

The Windows system records:

* Login event
* File access event

These are **Host-Centric Logs**.


# 2. Network-Centric Log Sources

These logs record activities that occur **across the network**.

### Devices

* Firewalls
* Routers
* Switches
* IDS/IPS
* VPN Servers
* Proxy Servers

### Common Events

* SSH connections
* FTP transfers
* Web traffic
* VPN connections
* Network file sharing

### Example

A user visits:

```text
https://example.com
```

The firewall or proxy records:

* Source IP
* Destination IP
* Website accessed
* Time
* Action (Allowed/Blocked)

These are **Network-Centric Logs**.


# Host vs Network Log Sources

| Host-Centric                         | Network-Centric                   |
| ------------------------------------ | --------------------------------- |
| Generated inside a device.           | Generated by network devices.     |
| Focuses on user and system activity. | Focuses on network communication. |
| Example: Windows Event Logs.         | Example: Firewall Logs.           |

# Challenges Without SIEM

If every device stores its own logs, security investigations become difficult.

## 1. Numerous Log Sources

Large organizations have hundreds or thousands of devices.

Each device generates hundreds or thousands of logs every second.

Checking every device manually is almost impossible.

## 2. No Centralization

Logs remain stored on the devices that generated them.

To investigate an incident, analysts may need to connect to multiple devices using:

* SSH
* RDP
* Remote Console

This wastes valuable investigation time.

## 3. Limited Context

One log usually doesn't tell the complete story.

Multiple logs from different devices must be combined.

### Example

Individually:

* Firewall shows an SSH connection.
* Windows shows a file access.
* VPN shows a remote login.

Each event appears normal.

When correlated:

* Attacker connects through VPN.
* Uses SSH for lateral movement.
* Accesses confidential files.

Now the attack becomes obvious.


## 4. Limited Manual Analysis

Modern networks generate **millions of logs every day**.

Humans cannot manually analyze every log.

Important attacks may be missed.

## 5. Different Log Formats

Different devices produce logs in different formats.

Examples:

* Windows Event Logs
* Linux Syslog
* Apache Logs
* Firewall Logs

Security analysts would need to understand every format, making investigations much harder.


# Why is This a Problem?

Without a centralized solution:

* Logs are scattered across devices.
* Investigations are slow.
* Events cannot be correlated easily.
* Analysts may miss attacks.
* Different log formats increase complexity.

These limitations are the main reason organizations use a **SIEM (Security Information and Event Management)** system.

-------------

# What is SIEM?

A **SIEM (Security Information and Event Management)** is a security solution that:

* Collects logs from different devices.
* Converts logs into a common format.
* Correlates related events.
* Detects suspicious activities.
* Generates alerts for security analysts.

Instead of checking logs on every device separately, analysts can investigate everything from one central platform.

# Main Features of SIEM

## 1. Centralized Log Collection

**Purpose:** Collect logs from all devices into one central location.

Instead of logging into every system, SIEM gathers logs automatically using:

* Agents
* APIs
* Log forwarding

### Log Sources

* Windows
* Linux
* Firewalls
* Routers
* Servers
* Web Servers
* Databases

### Benefits

* One place for all logs.
* Faster investigations.
* No need to access every device separately.

## 2. Log Parsing and Normalization

Different devices generate logs in different formats.

For example:

* Windows Event Logs
* Linux Syslog
* Apache Access Logs

These formats are different and difficult to analyze together.

SIEM solves this using **Parsing** and **Normalization**.

### Parsing

**Parsing** means breaking a raw log into individual fields.

Example:

Raw Log

```text id="ikz3u3"
192.168.1.10 - GET /login 200
```

After Parsing

| Field       | Value        |
| ----------- | ------------ |
| Source IP   | 192.168.1.10 |
| Method      | GET          |
| URL         | /login       |
| Status Code | 200          |


### Normalization

**Normalization** means converting logs from different devices into one common format.

This allows SIEM to analyze all logs consistently.

### Benefits

* Easy searching.
* Easy filtering.
* Easy comparison between different log sources.

# 3. Correlation of Logs

A single log rarely tells the full story.

SIEM combines related logs from multiple devices to identify suspicious patterns.

This process is called **Correlation**.

## Example

Within five minutes:

* Haris logs in through VPN from a new IP address.
* Haris accesses confidential files.
* Haris executes a PowerShell script.
* The computer makes an unusual outbound network connection.

Individually, these events seem normal.

Together, SIEM correlates them and detects a possible **data exfiltration attack** using compromised VPN credentials.

# 4. Real-Time Alerting

SIEM contains **Detection Rules**.

These rules continuously monitor incoming logs.

When a rule matches suspicious activity, SIEM automatically generates an alert.

The SOC analyst is then notified for investigation.


## Example

Detection Rule

```text id="xg54nd"
If Failed Login Attempts > 10
Within 1 Minute
Generate Alert
```

Possible Result

* Brute Force Attack Detected

# 5. Dashboards and Reporting

SIEM displays important security information using dashboards.

Dashboards provide a quick overview of the organization's security status.

### Common Dashboard Information

* Alert summary
* Failed login attempts
* System health
* Rules triggered
* Events collected
* Top visited domains
* Security notifications

### Benefits

* Easy monitoring.
* Faster decision-making.
* Better visibility of the network.

# Behind Triggered Alerts

A SIEM does not automatically "know" that an attack is happening.

It detects threats using **Detection Rules**.

These rules continuously monitor incoming logs.

When the conditions of a rule are met, the SIEM generates an **alert** for the SOC analyst.



# What is a Detection Rule?

A **Detection Rule** is a logical condition that tells the SIEM what suspicious activity to look for.

If the rule matches incoming logs, an alert is generated.

Think of it as:

> **IF a condition is TRUE → Generate an Alert**

  

# Examples of Detection Rules

### Rule 1: Multiple Failed Logins

```text
IF Failed Login Attempts ≥ 5
Within 10 Seconds

THEN

Generate Alert:
"Multiple Failed Login Attempts"
```

Possible Attack:

* Brute Force Attack

  

### Rule 2: Successful Login After Multiple Failures

```text
IF
Multiple Failed Logins

AND

Successful Login

THEN

Generate Alert:
"Successful Login After Multiple Failed Attempts"
```

Possible Attack:

* Password Guessing
* Brute Force Success

  

### Rule 3: USB Detection

```text
IF USB Device Connected

THEN

Generate Alert:
"USB Device Connected"
```

Useful when company policy prohibits USB devices.

  

### Rule 4: Large Outbound Traffic

```text
IF
Outbound Traffic > 25 MB

THEN

Generate Alert:
"Potential Data Exfiltration"
```

Possible Attack:

* Data Theft
* Data Exfiltration

 

# How is a Detection Rule Created?

A detection rule uses specific **fields** from normalized logs.

Common fields include:

* Log Source
* Event ID
* Username
* Process Name
* IP Address
* Destination
* Timestamp

The SIEM monitors these fields continuously.

  

# Use Case 1: Event Log Cleared

Attackers often delete Windows Event Logs after compromising a system to hide their activities.

Windows generates:

| Event ID | Meaning           |
| -------- | ----------------- |
| **104**  | Event Log Cleared |

Detection Rule

```text
IF

Log Source = WinEventLog

AND

Event ID = 104

THEN

Generate Alert:
"Event Log Cleared"
```

Possible Attack:

* Anti-Forensics
* Log Deletion

  

# Use Case 2: WHOAMI Command Execution

Attackers frequently execute:

```bash
whoami
```

after gaining access to determine their current privileges.

Windows records process creation using:

| Event ID | Meaning         |
| -------- | --------------- |
| **4688** | Process Created |

Detection Rule

```text
IF

Log Source = WinEventLog

AND

Event ID = 4688

AND

NewProcessName contains "whoami"

THEN

Generate Alert:
"WHOAMI Command Execution"
```

Possible Attack:

* Enumeration
* Privilege Discovery

  

# Why is Normalization Important?

Different devices generate different log formats.

SIEM first **normalizes** all logs into one standard format.

After normalization, detection rules can search the same fields across every log source.

Without normalization, writing detection rules would be much more difficult.

  

# Alert Investigation

Once SIEM generates an alert, the SOC analyst begins the investigation.

The analyst checks:

* Events related to the alert.
* Detection rule that triggered.
* Timeline of activities.
* Source and destination systems.

Finally, the analyst decides whether the alert is:

* False Positive
* True Positive

  

# 1. False Positive

A **False Positive** occurs when the alert looks suspicious but is actually legitimate.

### Example

An administrator intentionally runs:

```bash
whoami
```

The SIEM generates an alert.

After investigation, the analyst confirms it was normal administrative work.

Result:

* Close the alert.
* Tune the detection rule if necessary.

  

# 2. True Positive

A **True Positive** occurs when the suspicious activity is actually malicious.

### Example

An attacker executes:

```bash
whoami
```

immediately after exploiting a vulnerable server.

The SIEM detects this.

The analyst confirms the compromise.

Result:

* Continue the investigation.
* Begin incident response.

 

# Common Analyst Actions

If the alert is **False Positive**

* Close the alert.
* Improve (tune) the detection rule to reduce similar false alerts.

 

If the alert is **True Positive**

* Investigate further.
* Contact the system (asset) owner.
* Confirm suspicious activity.
* Isolate the infected host.
* Block the malicious IP address.
* Begin incident response.
