# Introduction to Incident Response

Organizations use many security measures such as:

* Firewalls
* Antivirus
* SIEM
* EDR
* IDS/IPS

These help **prevent cyber attacks**, but **no security is 100% perfect**.

Attackers may still bypass these defenses and compromise systems.

When this happens, the organization must know **how to detect, contain, investigate, and recover from the attack**.

This process is called **Incident Response (IR).**


# What is Incident Response?

**Incident Response (IR)** is the process of preparing for, detecting, responding to, and recovering from cybersecurity incidents.

Its main goal is to:

* Detect attacks quickly.
* Minimize damage.
* Recover systems.
* Prevent similar incidents in the future.


# Why is Incident Response Important?

Even with strong security controls, attacks can still happen.

Without an Incident Response plan:

* Attacks may spread.
* More systems may become infected.
* Sensitive data may be stolen.
* Recovery may take much longer.

A good Incident Response process reduces the impact of cyber attacks.


# Example

Imagine a company is infected with ransomware.

Without Incident Response:

* The malware spreads across the network.
* Files become encrypted.
* Business operations stop.

With Incident Response:

* The infected systems are isolated.
* The malware is removed.
* Data is restored from backups.
* The attack is investigated to prevent future incidents.


# What is a Security Incident?

A **Security Incident** is any event that threatens the **Confidentiality, Integrity, or Availability (CIA)** of an organization's systems or data.

Examples include:

* Malware infection
* Ransomware attack
* Data breach
* Phishing attack
* Unauthorized access
* Denial-of-Service (DoS) attack
------------

# Events, Logs, Alerts, and Incidents

Every action performed on a computer, laptop, server, or mobile device creates an **event**.

These events help security teams understand what is happening on a system.


# What is an Event?

An **Event** is any activity that occurs on a device or application.

Events can be generated by:

* Users
* Applications
* Operating System
* Background services


## Examples of Events

* User logs in.
* User logs out.
* File is created.
* File is deleted.
* Program starts.
* USB device is connected.
* Browser is opened.

Every one of these actions is considered an **event**.

# Interactive vs Non-Interactive Processes

Processes running on a system are generally of two types.

### Interactive Processes

These require user interaction.

Examples:

* Playing a game.
* Watching a video.
* Opening Microsoft Word.
* Browsing the Internet.


### Non-Interactive Processes

These run automatically in the background.

Examples:

* Windows Update
* Antivirus scanning
* Backup service
* System services

Although users don't interact with them, they still generate events.



# What is a Log?

A **Log** is a recorded event.

When an event occurs, the operating system or application stores it in a log file.

Think of a log as a **history record** of everything that happened on a system.


# Why Are Logs Important?

A single computer can generate **thousands or even millions of logs every day**.

Logs help investigators:

* Detect attacks.
* Investigate incidents.
* Troubleshoot problems.
* Monitor system activity.

# Security Solutions

Manually reviewing millions of logs is impossible.

Security tools automatically collect and analyze logs.

Examples include:

* SIEM
* EDR
* XDR

These tools look for suspicious patterns in the logs.


# What is an Alert?

An **Alert** is a notification generated by a security tool when it detects suspicious activity.

The alert tells the security team:

> "Something unusual happened. Please investigate."

An alert **does not always mean an attack has occurred**.

# False Positive

A **False Positive** is an alert that looks suspicious but is actually harmless.

After investigation, the activity is found to be legitimate.


## Example

A SIEM generates an alert because a large amount of data is being transferred.

After investigation, analysts discover:

* The company is performing a scheduled cloud backup.

The activity is legitimate.

**Result:** False Positive


# True Positive

A **True Positive** is an alert that correctly identifies a real security threat.

After investigation, the activity is confirmed to be malicious.


## Example

The SIEM detects a phishing email.

Investigation confirms:

* The email is malicious.
* It contains a fake login page.

**Result:** True Positive

# Incident

Once an alert is confirmed to be a **True Positive**, it becomes a **Security Incident**.

An **Incident** is a confirmed security event that requires response.
 

# Incident Severity

Organizations may experience multiple incidents at the same time.

Since security teams cannot respond to all incidents simultaneously, each incident is assigned a **severity level**.

Severity helps determine which incident should be handled first.

 

# Severity Levels

## Low

Small impact on the organization.

Example:

* Antivirus detects a harmless test file.

 

## Medium

Moderate impact.

May require investigation but is not immediately dangerous.

Example:

* Multiple failed login attempts.

 

## High

Serious incident requiring immediate attention.

Example:

* Malware infection on an employee's computer.

 

## Critical

The highest priority.

Can significantly impact the organization.

Examples:

* Ransomware attack
* Domain Controller compromise
* Large-scale data breach

Critical incidents are handled first.

# Common Types of Security Incidents

Not every cyber attack is simply called **"hacking."**

In cybersecurity, security incidents are classified into different types based on **how the attack happens** and **what its goal is**.

An organization may experience one or multiple types of incidents at the same time.

# 1. Malware Infection

**Malware** is malicious software designed to damage, disrupt, or gain unauthorized access to a system.

It is one of the most common security incidents.

### Common Types of Malware

* Virus
* Worm
* Trojan
* Ransomware
* Spyware
* Rootkit

### How Malware Spreads

* Malicious email attachments
* Fake software downloads
* Infected USB drives
* Malicious websites

### Example

A user downloads a fake PDF attachment from a phishing email.

The file installs ransomware and encrypts all company files.

# 2. Security Breach

A **Security Breach** occurs when an **unauthorized person gains access to confidential systems or data**.

The attacker successfully bypasses security controls.

### Examples

* Hacker logs into an employee account.
* Attacker gains access to a company database.
* Unauthorized access to confidential documents.

> **Goal:** Gain unauthorized access.


# 3. Data Leak

A **Data Leak** occurs when confidential information is **exposed or disclosed to unauthorized people**.

Unlike a Security Breach, a Data Leak **does not always involve an attacker**.

It may happen accidentally.

### Causes

* Human error
* Misconfigured cloud storage
* Sending confidential files to the wrong person
* Attacker publishing stolen data

### Example

An employee accidentally uploads customer records to a public cloud folder.



# Security Breach vs Data Leak

| Security Breach              | Data Leak                                     |
| ---------------------------- | --------------------------------------------- |
| Unauthorized access to data. | Confidential data becomes exposed.            |
| Usually caused by attackers. | Can be caused by attackers or human mistakes. |


# 4. Insider Attack

An **Insider Attack** is performed by **someone inside the organization**.

The attacker already has legitimate access to company resources.

### Examples

* Employee steals confidential data.
* Disgruntled employee installs malware.
* Administrator abuses privileged access.

Because insiders already have access, these attacks can be difficult to detect.


# 5. Denial of Service (DoS) Attack

A **Denial of Service (DoS)** attack attempts to make a system or service **unavailable** to legitimate users.

The attacker floods the target with excessive requests until it can no longer respond.

### Target

* Website
* Server
* Application
* Network

### Example

A website normally receives **500 requests per minute**.

An attacker sends **500,000 fake requests per minute**.

The server becomes overloaded and stops responding to real users.


# What Does DoS Affect?

A DoS attack mainly targets the **Availability** part of the **CIA Triad**.

The **CIA Triad** consists of:

* **Confidentiality** → Protect data from unauthorized access.
* **Integrity** → Ensure data is not modified improperly.
* **Availability** → Ensure systems and data remain accessible.

A successful DoS attack reduces **Availability**.


# Can Multiple Incidents Occur Together?

Yes.

One attack may involve multiple incident types.

### Example

```text
Phishing Email
      │
      ▼
Malware Installed
      │
      ▼
Security Breach
      │
      ▼
Sensitive Data Stolen
      │
      ▼
Data Leak
```

A single attack can result in:

* Malware Infection
* Security Breach
* Data Leak

 

# Does Every Incident Have the Same Severity?

No.

The severity depends on the organization.

### Example

Company A

* Online shopping website.
* A DoS attack stops customers from placing orders.
* Huge financial loss.

**Severity:** Critical

 

Company B

* Internal training website.
* Temporary downtime has little business impact.

**Severity:** Low or Medium

The same type of incident can have different impacts depending on the organization's business.

# Incident Response Frameworks

Different types of security incidents require a **structured response process**.

Instead of responding randomly, organizations follow **Incident Response Frameworks**, which provide step-by-step guidelines for handling incidents.

The two most widely used frameworks are:

* **SANS Incident Response Framework**
* **NIST Incident Response Framework**


# Why Do We Need an Incident Response Framework?

An Incident Response Framework helps organizations:

* Respond consistently to incidents.
* Reduce damage.
* Recover systems quickly.
* Improve future security.

Without a framework, incident handling may become slow and unorganized.


# SANS Incident Response Framework (PICERL)

The **SANS** framework has **6 phases**.

You can remember them using:

```text id="a9g3m1"
PICERL
```

* **P** → Preparation
* **I** → Identification
* **C** → Containment
* **E** → Eradication
* **R** → Recovery
* **L** → Lessons Learned


# 1. Preparation

The **Preparation** phase happens **before an incident occurs**.

The goal is to prepare the organization for future attacks.

### Activities

* Create an Incident Response Team.
* Develop an Incident Response Plan.
* Deploy security tools (SIEM, EDR, Firewall).
* Train employees.
* Create backups.

### Example

Employees receive phishing awareness training to help them recognize malicious emails.


# 2. Identification

The **Identification** phase focuses on detecting whether a security incident has occurred.

The security team investigates alerts generated by security tools.

### Activities

* Monitor logs.
* Investigate alerts.
* Confirm incidents.
* Determine incident severity.

### Example

The SIEM detects unusually large outbound network traffic.

Investigation reveals that malware is stealing company data.

# 3. Containment

Once the incident is confirmed, the next goal is to **stop it from spreading**.

Containment minimizes the damage.

### Activities

* Disconnect infected computers.
* Disable compromised accounts.
* Block malicious IP addresses.
* Isolate affected systems.

### Example

An infected laptop is disconnected from the network to stop the malware from spreading.

# 4. Eradication

After containing the attack, investigators remove the root cause of the incident.

### Activities

* Remove malware.
* Delete malicious files.
* Patch vulnerabilities.
* Close exploited security gaps.

### Example

The antivirus removes the ransomware from the infected computer.

# 5. Recovery

After the threat has been removed, systems are restored to normal operation.

### Activities

* Restore data from backups.
* Rebuild compromised systems.
* Verify systems are secure.
* Return systems to production.

### Example

The compromised server is rebuilt and restored using clean backups.

# 6. Lessons Learned

This is the final phase.

The organization reviews the incident to improve future security.

### Activities

* Conduct post-incident meetings.
* Perform Root Cause Analysis (RCA).
* Improve security controls.
* Update Incident Response procedures.

### Example

The investigation finds that the attack started because an employee clicked a phishing email.

The company improves phishing awareness training.

# SANS Workflow

```text id="v7b3qd"
Preparation
      │
      ▼
Identification
      │
      ▼
Containment
      │
      ▼
Eradication
      │
      ▼
Recovery
      │
      ▼
Lessons Learned
```

# NIST Incident Response Framework

The **NIST** framework is very similar to SANS but combines some phases.

It has **4 phases**.


## 1. Preparation

Prepare the organization before incidents occur.

## 2. Detection and Analysis

This combines:

* Identification
* Investigation
* Analysis

The security team confirms and analyzes incidents.

## 3. Containment, Eradication, and Recovery

NIST combines these three phases into one.

Activities include:

* Isolate affected systems.
* Remove threats.
* Restore systems.


## 4. Post-Incident Activity

Equivalent to **Lessons Learned** in the SANS framework.

The organization reviews the incident and improves its security processes.


# SANS vs NIST

| SANS            | NIST                                |
| --------------- | ----------------------------------- |
| Preparation     | Preparation                         |
| Identification  | Detection & Analysis                |
| Containment     | Containment, Eradication & Recovery |
| Eradication     | Containment, Eradication & Recovery |
| Recovery        | Containment, Eradication & Recovery |
| Lessons Learned | Post-Incident Activity              |

# Incident Response Plan (IRP)

An **Incident Response Plan (IRP)** is a formal document that explains **how an organization should respond to security incidents**.

It is approved by senior management and provides clear procedures for handling incidents before, during, and after they occur.


# Why is an IRP Important?

An IRP ensures that everyone knows:

* What to do.
* Who is responsible.
* Who should be contacted.
* How incidents should be handled.

This reduces confusion during emergencies.

# Key Components of an IRP

### 1. Roles and Responsibilities

Defines who performs each task.

Example:

* SOC Analyst
* Incident Responder
* Security Manager
* IT Administrator

### 2. Incident Response Methodology

Describes the steps to follow during an incident.

Many organizations base this on the **SANS** or **NIST** framework.

### 3. Communication Plan

Defines who should be informed during an incident.

Examples:

* Management
* Employees
* Customers
* Law Enforcement
* Regulatory Authorities

### 4. Escalation Path

Defines how incidents move to higher-level teams.

Example:

```text id="vq7xcy"
SOC Analyst L1
       │
       ▼
SOC Analyst L2
       │
       ▼
SOC Analyst L3
       │
       ▼
Incident Response Team
```

Critical incidents are escalated immediately.

# Incident Detection and Response Tools

Detecting cyber attacks manually is very difficult because organizations generate **millions of logs and events every day**.

To solve this problem, organizations use specialized **security tools** that automatically detect suspicious activities and, in some cases, respond to them.

 

# Common Incident Detection Tools

## 1. SIEM (Security Information and Event Management)

**Purpose:** Collects logs from multiple devices and analyzes them to detect suspicious activities.

### What SIEM Does

* Collects logs from different systems.
* Correlates events from multiple sources.
* Detects suspicious behavior.
* Generates alerts for security teams.

### Example

A user logs in from India and, five minutes later, another login occurs from the USA.

The SIEM correlates these events and generates an alert for a possible account compromise.

> **Main Role:** Detection

 

## 2. Antivirus (AV)

**Purpose:** Detects and removes known malware from a system.

### What Antivirus Does

* Scans files.
* Detects viruses and malware.
* Quarantines or removes infected files.
* Performs scheduled system scans.

### Example

A user downloads an infected file.

The antivirus detects the malware and quarantines the file before it can execute.

> **Main Role:** Malware Detection and Removal

 

## 3. EDR (Endpoint Detection and Response)

**Purpose:** Protects individual endpoints (computers, laptops, servers) from advanced threats.

Unlike Antivirus, EDR can both **detect and respond** to attacks.

### What EDR Does

* Monitors endpoint activity.
* Detects advanced attacks.
* Isolates infected systems.
* Terminates malicious processes.
* Removes malware.
* Supports incident investigation.

### Example

An employee's laptop becomes infected with ransomware.

The EDR automatically:

* Detects the ransomware.
* Disconnects the laptop from the network.
* Stops the malicious process.
* Alerts the SOC team.

> **Main Role:** Detection + Response

 

# Tool Comparison

| Tool               | Purpose                                                      |
| ------------------ | ------------------------------------------------------------ |
| **SIEM**           | Collects and analyzes logs to detect security incidents.     |
| **Antivirus (AV)** | Detects and removes known malware.                           |
| **EDR**            | Detects, investigates, and responds to threats on endpoints. |

 

# What is a Playbook?

A **Playbook** is a **high-level guide** that explains how to respond to a specific type of security incident.

It provides a standard procedure so that every incident is handled consistently.

Think of it as a **checklist** for incident response.

 

# Example: Phishing Email Playbook

1. Notify the security team and stakeholders.
2. Analyze the email header and content.
3. Examine attachments or links.
4. Check whether any user opened the attachment or clicked the link.
5. Isolate infected systems.
6. Block the sender's email address.
7. Continue investigation and recovery.

 

# What is a Runbook?

A **Runbook** contains the **detailed, step-by-step technical instructions** for completing a specific task from a Playbook.

A Playbook tells you **what** to do.

A Runbook tells you **exactly how** to do it.

 

# Playbook vs Runbook

| Playbook                            | Runbook                                     |
| ----------------------------------- | ------------------------------------------- |
| High-level response guide.          | Detailed technical procedure.               |
| Describes **what** actions to take. | Describes **how** to perform each action.   |
| Used for an entire incident.        | Used for specific tasks within an incident. |

 

## Example

### Playbook (Phishing Incident)

* Analyze the email.
* Check attachments.
* Isolate infected systems.
* Block the sender.

### Runbook (Isolate Infected System)

1. Open the EDR console.
2. Search for the affected endpoint.
3. Select the device.
4. Click **Isolate Host**.
5. Verify the device is disconnected from the network.
6. Document the action.

The **Playbook** tells you *what* should happen, while the **Runbook** provides the exact technical steps to perform it.
