# Hash Values

The **Pyramid of Pain** is a cybersecurity concept that explains **how difficult it is for an attacker to change the Indicators of Compromise (IOCs) defenders use to detect them**.

An **IOC (Indicator of Compromise)** is evidence that may show malicious activity has occurred.

Examples include:

* File hashes
* IP addresses
* Domain names
* Network artifacts
* Tools
* Attacker techniques

The main idea is:

> **The higher we move in the Pyramid of Pain, the harder and more painful it becomes for an attacker to change their behavior.**

For a **Threat Hunter, Incident Responder, or SOC Analyst**, this concept helps identify **which indicators are more valuable for long-term detection**.

# What is a Hash?

A **hash** is a fixed-length value generated from data using a **hashing algorithm**.

Think of a hash as a **digital fingerprint of a file**.

For example, a malware file may have a hash such as:

`D1A008E3A606F24590A02B853E955CF7`

Security analysts can use this hash to identify the specific file.

If the same file appears on another computer, its hash should normally be the same.

Simply remember:

> **File → Hashing Algorithm → Fixed-Length Hash Value**

## Common Hashing Algorithms

| Algorithm | Hash Size | Hexadecimal Length | Security Status                       |
| --------- | --------: | -----------------: | ------------------------------------- |
| MD5       |   128-bit |      32 characters | Not cryptographically secure          |
| SHA-1     |   160-bit |      40 characters | Deprecated for cryptographic security |
| SHA-256   |   256-bit |      64 characters | Stronger and widely used              |

### MD5

**MD5 (Message Digest 5)** was designed by Ron Rivest in 1992.

It produces a **128-bit hash value**, normally displayed as **32 hexadecimal characters**.

MD5 is no longer considered cryptographically secure because of weaknesses such as **hash collisions**.

A **hash collision** happens when **two different inputs produce the same hash value**.

Simple meaning:

> **Different File A and File B → Same Hash**

That is a security problem for a cryptographic hash function.

### SHA-1

**SHA-1 (Secure Hash Algorithm 1)** produces a **160-bit hash value**.

It is normally displayed as **40 hexadecimal characters**.

The National Institute of Standards and Technology deprecated SHA-1 for cryptographic uses because of its security weaknesses.

Stronger algorithms from the **SHA-2 and SHA-3 families** are preferred.

### SHA-2 and SHA-256

**SHA-2** is a family of hashing algorithms.

One of its most commonly used variants is **SHA-256**.

SHA-256 produces a **256-bit hash value**, normally displayed as **64 hexadecimal characters**.

Simply remember:

**MD5 → 128 bits**

**SHA-1 → 160 bits**

**SHA-256 → 256 bits**

# Why Do Security Analysts Use Hashes?

Security professionals use file hashes to **identify and reference suspicious or malicious files**.

Suppose a security researcher analyzes malware and finds its SHA-256 hash.

The researcher can share that hash with other security teams.

A SOC analyst can then search company systems for the same hash.

The process is:

**Known Malware Hash → Search Systems → Find Matching File → Investigate**

Hashes are commonly included in:

* Malware reports.
* Ransomware reports.
* Threat intelligence reports.
* Incident response investigations.

Analysts can also search hashes using services such as [VirusTotal](https://www.virustotal.com/?utm_source=chatgpt.com) and [MetaDefender Cloud](https://metadefender.opswat.com/?utm_source=chatgpt.com).

# Hashes as Indicators of Compromise

Suppose malware has this MD5 hash:

`D1A008E3A606F24590A02B853E955CF7`

A security team creates a detection rule:

> If a file with this hash is found, generate an alert.

This works well for **that exact malware file**.

However, there is a major problem.

An attacker can make a very small modification to the file.

Even changing **one bit or adding some data** can produce a completely different hash.


# Example: Changing a File Hash

First, the analyst calculates the MD5 hash of a file.

```powershell
Get-FileHash .\OpenVPN_2.5.1_I601_amd64.msi -Algorithm MD5
```

The original hash is:

`D1A008E3A606F24590A02B853E955CF7`

Now some text is appended to the file:

```powershell
echo "AppendTheHash" >> .\OpenVPN_2.5.1_I601_amd64.msi
```

The hash is calculated again:

```powershell
Get-FileHash .\OpenVPN_2.5.1_I601_amd64.msi -Algorithm MD5
```

The new hash is:

`9D52B46F5DE41B73418F8E0DACEC5E9F`

Notice what happened:

**Before modification:** `D1A008E3A606F24590A02B853E955CF7`

**After modification:** `9D52B46F5DE41B73418F8E0DACEC5E9F`

A small modification produced a **completely different hash**.

# Why Are Hashes at the Bottom of the Pyramid of Pain?

Hashes are considered **easy for attackers to change**.

Imagine a security tool detects malware using this hash:

**Malware Hash A → Detected**

The attacker slightly modifies the malware.

Now:

**Modified Malware → Hash B → Old hash detection no longer matches**

The attacker may not need to completely redesign their attack technique. They may only need to modify the file.

Therefore, using only file hashes for threat hunting can be weak against malware that is frequently modified.

This is why **Hash Values are at the bottom of the Pyramid of Pain**.

> **Low on Pyramid = Easy for attacker to change**

> **High on Pyramid = Hard for attacker to change**

# Pyramid of Pain – IP Addresses

An **IP address** is used to identify a device connected to a network.

Devices with IP addresses can include:

* Computers.
* Servers.
* Routers.
* Mobile devices.
* CCTV cameras.

Devices use IP addresses to **send and receive network data**.

In the **Pyramid of Pain**, IP addresses are another type of **Indicator of Compromise (IOC)**.

## Why Are IP Addresses Useful for Defenders?

Attackers often use remote infrastructure during an attack.

For example, a compromised computer may connect to an attacker's **Command and Control (C2 or C&C) server**.

The connection may look like:

**Compromised Computer → Malicious IP Address → C2 Server**

If a security analyst identifies the attacker's IP address, the organization can block it on the firewall.

For example:

**Malicious IP: `10.x.x.x` → Firewall blocks connection**

Common defensive actions include:

* Block the IP address.
* Drop traffic from the IP.
* Deny inbound connections.
* Create firewall rules.
* Monitor systems that communicated with the IP.

This makes an attacker's current infrastructure less useful.

## Why Is IP Blocking Not Bulletproof?

**Bulletproof** here means completely reliable or impossible to bypass.

Blocking a malicious IP is useful, but it is not a perfect defense.

An experienced attacker can obtain a **new public IP address** and move their malicious infrastructure.

For example:

**Attacker IP A → Defender detects and blocks it**

The attacker changes infrastructure.

**Attacker IP B → Attacker continues operation**

The defender now needs to identify and block the new IP address.

Because attackers can change IP addresses, IP-based detection creates **some pain**, but not a huge amount of pain.

This is why IP addresses are shown in **green** in the Pyramid of Pain.

> **IP addresses are harder to change than a file hash, but attackers can still change them relatively easily.**

## Hash vs IP Address

| Hash                                                       | IP Address                                                      |
| ---------------------------------------------------------- | --------------------------------------------------------------- |
| Identifies a specific file.                                | Identifies a network host or endpoint.                          |
| Very easy for an attacker to change by modifying the file. | Requires the attacker to change or move network infrastructure. |
| Very low pain.                                             | Slightly more pain.                                             |

This is why **IP Addresses are above Hash Values in the Pyramid of Pain**.

# What is Fast Flux?

**Fast Flux** is a DNS technique commonly associated with botnets and malicious infrastructure.

Its main idea is:

> **One domain name is associated with many IP addresses that change frequently.**

Normally, a domain may resolve to a stable IP address.

**Example:** `example.com → IP Address A`

With Fast Flux, the IP addresses behind a domain frequently rotate.

**Example:** `malicious-domain.example → IP A → IP B → IP C → IP D`

The domain stays the same, but the associated IP addresses keep changing.

## Why Do Attackers Use Fast Flux?

Suppose defenders discover a malicious IP address and block it.

**Malicious IP A → Blocked**

The malicious domain may then resolve to another compromised host.

**Domain → IP B**

The defender blocks IP B.

The infrastructure changes again.

**Domain → IP C**

This makes simple IP blocking less effective.

Fast Flux can be used to hide infrastructure related to:

* Phishing.
* Malware delivery.
* Malware communication.
* Web proxying.
* Command and Control (C2) activity.

## How Fast Flux Works

A **botnet** is a network of compromised devices controlled by an attacker.

In a Fast Flux network, compromised devices may act as proxies between infected systems and the real malicious infrastructure.

The communication may work like this:

**Victim → Fast Flux Domain → Changing Compromised Host → C2 Server**

The compromised hosts hide the actual C2 infrastructure.

If one IP address is blocked or taken offline, another IP address can be used.

This makes the malicious infrastructure more **resilient (able to continue operating despite disruption)**.

## Simple Fast Flux Example

Suppose a malicious domain is `bad-domain.example`.

At 10:00 AM, it resolves to `IP Address A`.

At 10:05 AM, it resolves to `IP Address B`.

At 10:10 AM, it resolves to `IP Address C`.

The **domain remains the same**, but the IP address keeps changing.

This makes it harder for defenders to stop the malicious activity using only IP blocking.

## Fast Flux and DNS

**DNS (Domain Name System)** converts domain names into IP addresses.

Normal DNS example:

**Domain → IP Address**

Fast Flux abuses rapid DNS changes so that:

**One Domain → Many Frequently Changing IP Addresses**

The DNS records often use short lifetimes, allowing the associated IP addresses to change frequently.

## Why Are IP Addresses in the Pyramid of Pain?

IP addresses are useful IOCs because defenders can:

* Search network logs for connections.
* Identify infected systems.
* Block malicious traffic.
* Create firewall detection rules.

However, attackers can respond by:

* Changing public IP addresses.
* Moving servers.
* Using proxies.
* Using VPN infrastructure.
* Using Fast Flux networks.

Therefore, IP addresses create **more pain than hashes**, but attackers can still adapt.

# Host Artifacts

Now we move another level higher in the **Pyramid of Pain** into the **yellow zone: Host Artifacts**.

At this level, detection creates **more difficulty for the attacker**.

If defenders detect the attack using host artifacts, the attacker may need to **change tools, payload behavior, or attack methods**.

This can require more time and resources.

Simply remember:

> **Host Artifacts = Traces left by an attacker on a compromised system.**

## What are Host Artifacts?

**Host** means the computer or system being investigated.

**Artifact** means a trace or piece of evidence.

So:

> **Host Artifact = Evidence or traces of malicious activity found on a computer.**

When attackers or malware interact with a system, they often leave traces behind.

Examples include:

* Registry values.
* Suspicious processes.
* Files created or dropped.
* Modified files.
* Suspicious process relationships.
* Malware-specific patterns.
* Other IOCs related to the threat.

## Registry Values

The **Windows Registry** stores configuration information for Windows and applications.

Attackers may create or modify registry values.

For example, malware may modify a startup-related registry location so that it runs when a user logs in.

A security analyst may detect:

**New suspicious registry value → Unknown program configured to run → Investigate**

The registry modification becomes a **host artifact**.

## Suspicious Process Execution

A **process** is a running program.

Security analysts investigate unusual process activity.

For example:

**Microsoft Word → PowerShell**

This process relationship may be suspicious depending on the context.

Why?

A normal Word document usually does not need to launch PowerShell.

An attack could look like:

**Malicious Document → Word Opens → PowerShell Executes → Malicious Activity**

The unusual process execution becomes a host artifact.

The key idea is:

> **Analysts do not only look at the process name. They also look at how and why the process started.**

## Suspicious Events

A malicious application may cause several suspicious events on the system.

For example:

**Malicious File Opened → Process Created → System Changed → Network Connection Made**

One event alone may look normal.

However, multiple related events can create a suspicious **attack pattern**.

For example:

**Word → PowerShell → Downloads File → Executes File**

This pattern can indicate malicious activity.

## Files Dropped by Malware

A **dropped file** is a file created or placed on a system by malware or another malicious program.

For example:

**Malware Executes → Creates `payload.exe` → Executes `payload.exe`**

Here, `payload.exe` is a **dropped file**.

Malware may drop:

* Executable files.
* DLL files.
* Scripts.
* Configuration files.
* Temporary files.

Security analysts can investigate:

* File location.
* File name.
* File creation time.
* File modification time.
* File hash.
* Process that created the file.

## Modified Files

Attackers may also modify existing files.

For example:

**Original System File → Attacker Modifies File**

Or:

**Configuration File → Malware Changes Settings**

The modification becomes a host artifact.

Analysts may compare:

**Normal System State vs Current System State**

Unexpected changes can indicate malicious activity.

## Why Are Host Artifacts Higher in the Pyramid?

Consider hash detection.

**Malware Hash Detected → Attacker slightly modifies file → New hash**

Easy for the attacker.

Consider IP detection.

**Malicious IP Blocked → Attacker changes IP**

Still relatively easy.

But now imagine defenders detect this behavior:

**Word → PowerShell → Suspicious Script Execution → Malicious File Created**

The attacker cannot simply change one hash or IP.

They may need to:

* Change the malware.
* Change the execution method.
* Change process behavior.
* Change persistence techniques.
* Change file locations.
* Change attack methodology.

This creates **more pain for the attacker**.

# Pyramid of Pain – Network Artifacts

**Network Artifacts** are also in the **yellow zone** of the Pyramid of Pain.

A **Network Artifact** is a trace or pattern of malicious activity found in **network traffic**.

Simply remember:

> **Network Artifact = Suspicious evidence found in network communication.**

If defenders detect these patterns, attackers may need to **modify their malware, C2 communication, or tools**. This requires more time and effort.

## Examples of Network Artifacts

Common network artifacts include:

* **User-Agent strings**
* **C2 communication information**
* **URI patterns**
* **HTTP POST request patterns**

For example:

**Infected Computer → HTTP POST Request → C2 Server**

The malware may repeatedly send similar HTTP requests.

A SOC analyst can identify this pattern and create a detection rule.

## What is a User-Agent?

A **User-Agent** is a string sent in an HTTP request that provides information about the client making the request.

For example, a normal browser may send a User-Agent indicating that the request came from a particular browser and operating system.

A simplified example is:

`Mozilla/5.0 ... Chrome/...`

The server can use this information to understand which client made the request.

Malware may also send HTTP requests.

However, malware may use:

* A custom User-Agent.
* An unusual User-Agent.
* An outdated User-Agent.
* The same suspicious User-Agent repeatedly.

For example:

**Normal Environment → Mostly common browser User-Agents**

Suddenly:

**Unknown Process → Strange User-Agent → Repeated external connections**

This can be suspicious.

The important idea is:

> **A User-Agent not normally observed in the organization's environment may be worth investigating.**

An unusual User-Agent alone does **not automatically prove malware**. Analysts should investigate it with other evidence.


## C2 Information

**C2 means Command and Control.**

Attackers use C2 infrastructure to communicate with compromised systems.

For example:

**Attacker C2 Server ↔ Infected Computer**

The malware may:

* Receive commands.
* Send system information.
* Download payloads.
* Upload stolen data.

Analysts can examine the network traffic and identify patterns related to C2 communication.

These patterns become **network artifacts**.

## URI Patterns

**URI** means **Uniform Resource Identifier**.

In simple words, it identifies a resource or path used in a web request.

For example:

`/login`

`/api/update`

`/images/file.jpg`

Malware may repeatedly communicate with unusual URI paths.

For example:

`/gate.php`

`/update/check`

`/data/send`

If the same suspicious URI pattern appears across infected computers, analysts can use it as a network artifact.

Simply remember:

> **URI Pattern = Repeated or unusual web request path.**


## HTTP POST Request Patterns

The **HTTP POST** method is commonly used to send data to a web server.

Normal applications use POST requests for legitimate purposes such as login forms and API requests.

Malware can also use POST requests to send information to C2 infrastructure.

For example:

**Malware → HTTP POST → Sends system information → C2**

Analysts may observe repeated suspicious POST requests.

One request may not immediately identify the malware.

However, analysts can investigate:

* Destination host.
* User-Agent.
* URI.
* Request frequency.
* Request size.
* Process generating the traffic.

Combining these indicators can help identify malicious network behavior.

# Detecting Network Artifacts

Network artifacts can be found in **PCAP files**.

**PCAP** means **Packet Capture**.

A PCAP file contains captured network packets.

Simply remember:

> **PCAP = A saved recording of network traffic.**

Security analysts can analyze PCAP files using Wireshark or TShark.

Network artifacts can also be identified through IDS alerts from tools such as [Snort](https://www.snort.org/?utm_source=chatgpt.com).

**IDS means Intrusion Detection System.**

An IDS monitors network activity and generates alerts for suspicious behavior.


# TShark Command

To display HTTP request hosts and User-Agent strings from a PCAP file:

```bash
tshark --Y http.request -T fields -e http.host -e http.user_agent -r analysis_file.pcap
```

### Command Meaning

| Part                    | Meaning                   |
| ----------------------- | ------------------------- |
| `tshark`                | Start TShark              |
| `-Y http.request`       | Show HTTP request packets |
| `-T fields`             | Display selected fields   |
| `-e http.host`          | Display HTTP host         |
| `-e http.user_agent`    | Display User-Agent        |
| `-r analysis_file.pcap` | Read the PCAP file        |

So the command means:

> **Read the PCAP and show HTTP hosts and their User-Agent strings.**

# Emotet User-Agent Example

Emotet malware has been associated with identifiable network behaviors, including User-Agent patterns in some campaigns.

Suppose analysts identify a suspicious custom User-Agent repeatedly associated with malicious activity.

The defender can create a detection rule for that pattern.

**Malware User-Agent Detected → Alert Generated**

Now the attacker may need to modify the malware's network communication behavior.

This requires more effort than simply changing a file hash or IP address.


# Why Are Network Artifacts Higher in the Pyramid?

Consider the lower levels:

**Hash detected → Modify file**

**IP blocked → Change IP**

**Domain blocked → Change domain**

But suppose defenders detect:

**Specific User-Agent + Specific URI Pattern + Repeated POST Communication**

The attacker may need to:

* Modify malware code.
* Change HTTP request structure.
* Change User-Agent behavior.
* Change URI patterns.
* Change C2 communication methods.

This creates **more pain for the attacker**.

# Host Artifacts vs Network Artifacts

| Host Artifacts              | Network Artifacts          |
| --------------------------- | -------------------------- |
| Found on a computer/system. | Found in network traffic.  |
| Registry changes.           | User-Agent strings.        |
| Suspicious processes.       | C2 communication patterns. |
| Dropped files.              | URI patterns.              |
| Modified files.             | HTTP request patterns.     |

# Pyramid of Pain – Tools

Now we have reached the **challenging level for attackers: Tools**.

At this level, defenders are no longer detecting only simple indicators such as hashes, IP addresses, or domains.

They are detecting the **attacker's tools and their characteristics**.

Simply remember:

> **Tools = Software or utilities used by an attacker to perform malicious activities.**

When defenders successfully detect an attacker's tool, the attacker may need to **modify the tool, find a replacement, or develop a completely new tool**.

This creates significant pain for the attacker.

## What Are Attacker Tools?

Attackers use different tools for different stages of an attack.

Examples include tools used to:

* Create malicious documents.
* Generate payloads.
* Establish C2 communication.
* Create backdoors.
* Steal information.
* Crack passwords.
* Execute malicious code.

Attackers may use:

* Custom `.exe` files.
* DLL files.
* Scripts.
* Malware.
* Backdoors.
* Password crackers.

For example:

**Trojan Executes → Drops `Stealer.exe` in Temp Folder → Executes `Stealer.exe`**

Here, `Stealer.exe` may be a tool used to steal information.

The defender can analyze the tool and create detections for it.

## Malicious Macro Documents

A **malicious document (maldoc)** is a document containing malicious code or behavior.

Attackers may use malicious documents in **spearphishing attacks**.

**Spearphishing** is a targeted phishing attack against a specific person or organization.

A simplified attack may look like:

**Phishing Email → Malicious Document → User Opens File → Malicious Code Executes**

Historically, attackers have abused document features such as macros to execute malicious actions.

## Backdoors and C2 Tools

A **backdoor** provides hidden or unauthorized access to a system.

Attackers may use a backdoor to communicate with their **Command and Control (C2) infrastructure**.

For example:

**Compromised Computer ↔ Backdoor ↔ C2 Server**

Through C2 communication, an attacker may send commands to the compromised system.

If defenders identify characteristics of the backdoor or C2 tool, they can create detection rules.

The attacker may then need to replace or significantly modify the tool.
# Detecting Attacker Tools

Security teams can use several detection methods.

Important examples are:

* Antivirus signatures.
* Detection rules.
* YARA rules.
* Fuzzy hashing.

## Antivirus Signatures

An **antivirus signature** is a known pattern associated with malicious software.

The antivirus compares files or activity against known malicious patterns.

For example:

**File → Compare with Malware Signature → Match Found → Alert**

The file may then be blocked or quarantined.

A signature may identify specific characteristics of known malware.

## Detection Rules

A **detection rule** defines suspicious conditions that security tools should detect.

For example:

**Suspicious Process + Suspicious File Location + Unusual Execution → Generate Alert**

Detection rules may be used in:

* SIEM systems.
* EDR platforms.
* IDS/IPS systems.
* SOC monitoring tools.

For example:

**Executable created in Temp folder → Executed by suspicious process → Alert**

Detection rules can focus on more than a single file hash.

## YARA Rules

**YARA** is commonly used to identify and classify malware based on patterns.

A YARA rule can search for characteristics such as:

* Strings.
* Byte patterns.
* File characteristics.
* Combinations of conditions.

For example, imagine malware contains these unique strings:

`StealerConfig`

`SendCredentials`

`C2Server`

A YARA rule could look for a combination of these characteristics.

The idea is:

**File → YARA Rule Checks Patterns → Pattern Match → Suspicious File Identified**

This is useful because an attacker may change the file hash while some internal characteristics of the tool remain similar.

Simply remember:

> **YARA = Pattern-based file and malware identification.**

These resources may provide:

# Fuzzy Hashing

Normal cryptographic hashes have one major limitation.

Suppose we have:

**File A → Hash A**

The attacker slightly modifies the file.

**Modified File A → Completely Different Hash B**

The old hash-based detection may no longer match.

**Fuzzy hashing** helps solve a different problem: **file similarity analysis**.

Simply remember:

> **Fuzzy Hashing = Compare files to find how similar they are.**

## Normal Hash vs Fuzzy Hash

| Normal Hash                                 | Fuzzy Hash                                    |
| ------------------------------------------- | --------------------------------------------- |
| Checks exact file identity.                 | Checks file similarity.                       |
| Small change creates a very different hash. | Can identify similarity despite some changes. |
| Useful for exact matching.                  | Useful for similarity analysis.               |

Example:

**Original Malware → File A**

The attacker modifies a small part.

**Modified Malware → File B**

Normal hashing may say:

**File A ≠ File B**

Fuzzy hashing may indicate:

**File A and File B are highly similar**

This can help analysts identify malware variants.

# SSDeep

**SSDeep** is a tool used for fuzzy hashing and similarity analysis.

It generates fuzzy hashes that can be compared to estimate similarity between files.

For example:

**Malware Sample A → SSDeep Hash**

**Malware Sample B → SSDeep Hash**

SSDeep compares the fuzzy hashes.

The result can help indicate whether the files share similar content.

This is useful when attackers make minor modifications to malware.

## Simple Example

Imagine an attacker uses `Stealer.exe`.

The security team detects and blocks the tool.

The attacker changes a few parts of the file.

Now:

**Old Hash ≠ New Hash**

Normal hash detection may fail.

However:

**Fuzzy Hash Comparison → High Similarity**

The security analyst may identify the new file as a variant of the original tool.

Now the attacker may need to **significantly modify or completely replace the tool**.

This creates much more pain.

# Why Are Tools High in the Pyramid of Pain?

Consider the previous levels:

**Hash detected → Modify file**

**IP blocked → Change IP**

**Domain blocked → Change domain**

**Artifact detected → Change behavior or communication pattern**

But:

**Tool detected → Modify tool, replace tool, develop new tool, or learn another tool**

Developing a new tool may require:

* Time.
* Money.
* Programming skills.
* Testing.
* Training.

Therefore, tool-based detection creates significant difficulty for attackers.

# Pyramid Progress

| Level             | Attacker Pain |
| ----------------- | ------------- |
| Hash Values       | Very low      |
| IP Addresses      | Low           |
| Domain Names      | Moderate      |
| Host Artifacts    | Higher        |
| Network Artifacts | Higher        |
| **Tools**         | **Very high** |

# Pyramid of Pain – TTPs

We have reached the **top (apex) of the Pyramid of Pain: TTPs**.

**TTPs** stands for:

**Tactics, Techniques, and Procedures**

TTPs describe **how an attacker operates and performs an attack to achieve a goal**.

Simply remember:

> **TTPs = Attacker's behavior, methods, and way of performing an attack.**

TTPs are strongly connected with the MITRE ATT&CK knowledge base.


## Understanding Tactics, Techniques, and Procedures

| Term          | Simple Meaning                                | Question         |
| ------------- | --------------------------------------------- | ---------------- |
| **Tactic**    | Attacker's goal                               | **Why?**         |
| **Technique** | Method used to achieve the goal               | **How?**         |
| **Procedure** | Exact way the attacker performs the technique | **Exactly how?** |

### Tactic

A **Tactic** represents the attacker's objective or goal.

For example:

* Initial Access.
* Persistence.
* Credential Access.
* Lateral Movement.
* Data Exfiltration.

Suppose an attacker wants to steal passwords.

The attacker's goal is:

**Credential Access**

This is the **tactic**.

Simply remember:

> **Tactic = What goal does the attacker want to achieve?**


### Technique

A **Technique** describes the method the attacker uses to achieve the tactic.

For example:

**Tactic:** Credential Access

**Technique:** OS Credential Dumping

The attacker's goal is to obtain credentials, and credential dumping is one possible method.

Another example:

**Tactic:** Lateral Movement

**Technique:** Remote Services

Simply remember:

> **Technique = How does the attacker achieve the goal?**


### Procedure

A **Procedure** describes the specific implementation of a technique by an attacker or threat group.

For example:

**Tactic:** Credential Access

**Technique:** OS Credential Dumping

**Procedure:** A specific adversary uses a particular tool and command sequence to extract credentials from a compromised Windows system.

Simply remember:

> **Procedure = The attacker's specific way of performing the technique.**


# Simple TTP Example

Imagine an attacker wants to steal company data.

**Tactic:** Exfiltration

The attacker's goal is to remove data from the organization.

**Technique:** Exfiltration Over Web Service

The attacker uses a web-based service to transfer the data.

**Procedure:** The attacker uses a specific script or tool configuration to upload selected files to a particular service.

The relationship is:

**Tactic → Goal**

**Technique → Method**

**Procedure → Specific implementation**

# MITRE ATT&CK and TTPs

The [MITRE ATT&CK knowledge base](https://attack.mitre.org/?utm_source=chatgpt.com) documents adversary tactics and techniques based on observed threat behavior.

An attack may involve multiple stages.

For example:

**Phishing → Execution → Persistence → Credential Access → Lateral Movement → Exfiltration**

Each stage can contain different techniques.

Security teams use ATT&CK to understand:

* What attackers are trying to achieve.
* Which techniques attackers use.
* Which behaviors should be monitored.
* Where detection coverage may be missing.


# Pass-the-Hash Example

A **Pass-the-Hash (PtH) attack** is a technique where an attacker abuses a captured password hash for authentication rather than using the plaintext password.

For example:

**Compromised Host → Credential Material Obtained → Hash Abused for Authentication → Access Another System**

The attacker may use this to perform **lateral movement**.

**Lateral Movement** means moving from one compromised system to another system inside a network.

For example:

**Computer A → Computer B → Server C**

## Detecting Pass-the-Hash Behavior

Suppose the organization monitors Windows Event Logs.

The security team detects authentication activity that matches suspicious Pass-the-Hash behavior.

The process may be:

**Suspicious Authentication Detected → Investigate Host → Identify Compromised System → Contain Host → Stop Lateral Movement**

The defender is not simply detecting:

**One Hash**

or:

**One IP Address**

The defender is detecting **the attacker's behavior and technique**.

This is much harder for the attacker to bypass.


# Why Are TTPs at the Top of the Pyramid?

Suppose defenders block a malware hash.

The attacker modifies the file.

**Easy.**

Suppose defenders block an IP.

The attacker changes the IP.

**Still relatively easy.**

Suppose defenders detect the attacker's tool.

The attacker may replace the tool.

**Difficult.**

But suppose defenders detect the **actual attack technique**.

For example:

**Credential Theft → Pass-the-Hash → Lateral Movement**

Now the attacker may need to change their **entire attack methodology**.

They may need to:

* Research new techniques.
* Learn new attack methods.
* Reconfigure tools.
* Develop new tools.
* Change their attack workflow.
* Spend more time testing.

This creates the **maximum pain for the attacker**.

# Attacker's Options

If defenders can quickly detect and respond to TTPs, the attacker may have two main choices.

**Option 1:** Change the attack methodology.

The attacker may need to perform more research, learn new techniques, and modify their tools.

**Option 2:** Give up and attack another target.

For many attackers, finding another less-protected target may require fewer resources.


# Complete Pyramid of Pain

| Level             | What Defender Detects                 | Attacker Pain |
| ----------------- | ------------------------------------- | ------------- |
| Hash Values       | Exact malicious file                  | Very Low      |
| IP Addresses      | Malicious network IP                  | Low           |
| Domain Names      | Malicious domain                      | Moderate      |
| Host Artifacts    | System traces                         | Higher        |
| Network Artifacts | Network patterns                      | Higher        |
| Tools             | Attacker software                     | Very High     |
| **TTPs**          | **Attacker behavior and methodology** | **Maximum**   |

The basic idea is:

**Hash → IP → Domain → Host Artifact → Network Artifact → Tools → TTPs**

As we move upward:

**Detection becomes stronger**

and

**Attacker pain increases**
